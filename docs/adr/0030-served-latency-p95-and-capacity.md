# AD-30 — The served API has a p95 and a capacity number

> Part of the TrialGuard architectural decision log ([index](../../README.md#architectural-decision-log)). Amendments are appended here rather than replacing what they correct.

## Decision

The served API has a p95 and a capacity number, and the advertised latency describes the demo rather than the product. `production_readiness.md` declined to claim p95 on the grounds that a probe is n=1, which was the right refusal and left the SLO gating on a single request. A distribution is measurable from one client even though a load test is not -- `api_search_rate_per_min` is 10 per IP, so a conventional test would measure the limiter -- and at n=40 the warm path is **p50 787.3 ms, p95 981.9 ms wall** (server-side 703.8 / 859.3), nearest-rank so every figure is an observed request. The 1500 ms SLO holds with headroom rather than by luck. Two findings the median hid. **The cold path is 14x worse**: a user pasting an unseen note pays LLM keyword extraction first, median **10,973 ms** and worst 19,130 ms, of which 94% is `keyword_ms` while retrieval is unchanged at ~590 ms -- so "780 ms warm" describes the demo's preset buttons, and caching keywords for the presets made the demo fast without making the product fast. And **concurrency buys almost nothing**: across bursts of 2, 4 and 8 sized to fit inside one minute's budget, latency grows 1.84x / 3.55x / 6.80x while throughput stays flat at 1.27 to 1.45 req/s, so the service is effectively serial for search and eight concurrent callers queue rather than parallelise. That is consistent with `fanout_ms` being ~590-690 ms of a ~705 ms request: the 12-keyword fan-out already saturates the cores, so request concurrency contends with it instead of filling idle capacity. Practical capacity is **~1.4 searches/second, ~85/minute**, roughly 8 concurrent users on the current machine. [`e6_findings.md`](../../data/reports/e6_findings.md)

## Alternatives considered

Attempting a real load test from one host (measures the rate limiter, and on a shared daily budget risks taking the live demo dark); keeping the n=1 probe and continuing to decline a p95, when the distribution costs five minutes to measure; reporting the first cold-path run, which measured a 13.7 ms penalty because an earlier crash of this same harness had already issued every request and warmed the keyword cache -- a cold-path note is single-use, and the harness now writes raw samples before summarising so a reporting crash cannot cost the run
